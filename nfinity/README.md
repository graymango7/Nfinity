## 1. 지금 이게 뭔가요?

세 가지 프로그램이 서로 연결돼서 돌아갑니다.

- **PostgreSQL** — 데이터를 저장하는 곳. 유저, 거래 내역, 이상 거래 기록이 여기 저장됩니다.
- **Redis** — 아주 빠르게 읽고 쓰는 임시 저장소. 예산통제 기능에서 "이번 달 카테고리별로 얼마 썼는지"를 실시간으로 집계할 때 씁니다. (8/26부터 실제로 사용 시작 — `app/redis_client.py`)
- **FastAPI** — 우리가 만드는 서버. "이 거래 위험한가요?" 같은 질문을 받아서(API) 답을 주는 프로그램입니다.

**Docker**는 이 세 프로그램을 각자의 컴퓨터에 굳이 설치 안 해도, 명령어 한 줄로 통째로 띄워주는 도구입니다.

## 3. 실행 방법 (본인 컴퓨터에 Docker Desktop 필요)

```bash
cd sidegig_ai
cp .env.example .env
docker compose up --build -d
```

30초~1분 후 브라우저에서:

```
http://localhost:8000/docs
```

DB에 실제 데이터를 채워 넣으려면 (컨테이너가 뜬 상태에서):

```bash
pip install -r requirements.txt
export DATABASE_URL=postgresql://sidegig:sidegig_pw@localhost:5432/sidegig
python -m data_pipeline.ingestion         # mock_transactions.csv 4,978건 적재 (정제+카테고리분류 포함)
python -m scripts.build_user_profiles     # 유저별 실제 한도/평균 프로파일 계산
```

컨테이너 상태 확인: `docker compose ps` · 로그: `docker compose logs -f api` · 끄기: `docker compose down`

## 4. 실제로 검증한 것 (Docker 없이, 로컬 PostgreSQL 16으로 동일 코드 실행)

이 환경엔 Docker 데몬이 없어서 `docker compose up`은 직접 못 돌렸지만, **완전히 동일한 코드**로
로컬 PostgreSQL을 띄워 Day1(A)+Day2(B,C) 산출물을 전부 병합해서 처음부터 끝까지 실행했습니다.
`docker-compose.yml`/`Dockerfile`은 표준 구성이라 본인 컴퓨터에서도 그대로 동작할 거예요.

- ✅ `sql/init.sql` → 6개 테이블 정상 생성
- ✅ `data_pipeline/ingestion.py` → mock_transactions.csv **4,978건**(persona_map.csv 기준 유저 35명) 전부 정제→카테고리분류→적재 성공. 가맹점 23종이 `categorizer.py` 매핑에 전부 커버되어 "기타"로 새는 거래 0건.
- ✅ `scripts/build_user_profiles.py`(신규) → 35명 전원 실제 거래 기반 프로파일 계산 완료
- ✅ `tests/test_rule_engine.py` 6개 테스트 전부 통과
- ✅ `POST /api/v1/risk/assess` 실서버 기동 후 실제 HTTP 요청으로 확인
- 🐛 **버그 발견 & 수정**: `app/routers/risk.py`에서 여러 규칙이 동시에 걸렸을 때
  최종 `severity`/`action`을 뽑는 로직이 `max(results, key=lambda r: r.severity)`로
  **Severity를 알파벳 문자열 순으로 비교**하고 있었습니다. 그 순서가 `CRITICAL < HIGH < LOW < MEDIUM`이라,
  예를 들어 R001(HIGH)과 R002(CRITICAL)가 동시에 걸려도 최종 결과가 `MEDIUM`/`HIGH`처럼 실제보다
  낮게 나올 수 있었습니다 (심야에 한도초과+해외결제가 겹치는 등 흔히 일어나는 상황).
  → 심각도 랭킹표(`_SEVERITY_RANK`)로 교체해서 수정했고, 실제 API 응답으로 재확인했습니다
  (한도 초과 상황 테스트 → 이제 정확히 `CRITICAL`/`BLOCK` 반환). `GET /risk/score/{user_id}`의
  동시각 타이브레이크 문제도 같은 방식으로 같이 고쳤습니다.
- 📊 **룰 엔진만으로(ML 모델 붙이기 전)** mock 데이터 정답지 대비 정확도: **Precision 0.61 / Recall 0.65**.
  낮아 보이지만 정상입니다 — 정답지의 이상 유형 중 `R00y_신규기기`(기기 불일치)와 `R00x_위치급변`은
  애초에 설계서상 **Isolation Forest 몫**(rule 아님)이고, `R006_단기반복`은 3연타 이벤트 중
  처음 2건은 "아직 반복이 안 쌓인 시점"이라 규칙상 당연히 안 걸립니다(3번째부터 걸림 — 정상 동작).
  → (8/28 업데이트) 실제로 Isolation Forest를 붙이고 재검증한 결과는 아래 6-3번 참고 —
  Recall은 0.65→0.734로 올랐고, 그 과정에서 발견한 다른 이슈도 같이 정리했습니다.

### 실제로 검증한 것

로컬 PostgreSQL + Redis를 띄우고 7개 시나리오(예산 설정 → 지출 2건 기록 → 사용량 조회 →
예측 조회 → Gig-Score 조회 → 절세장부 스텁 호출 → 존재하지 않는 유저 에러 확인)를 실제
HTTP 요청으로 전부 통과 확인했습니다.

### 만들면서 발견해서 고친 것 2개

1. **`budgets` 테이블에 UNIQUE 제약이 없었습니다.** 원래 설계서에는 `UNIQUE(user_id,
   category, period)`가 있었는데 실제 `sql/init.sql`에는 빠져 있어서, 예산을 두 번 설정하면
   같은 유저·카테고리 행이 계속 늘어나는 상태였습니다. `sql/init.sql`에 제약을 추가하고
   (이미 테이블이 있는 사람을 위한 `ALTER` 보강문도 같이 넣었습니다), `ON CONFLICT ...
   DO UPDATE`로 "이미 있으면 갱신"이 되도록 고쳤습니다.
2. `get_usage()`에서 존재하지 않는 `is_active` 컬럼을 조회 조건에 걸어서 처음엔 에러가
   났습니다 (설계서 원본 스키마와 실제 `budgets` 테이블이 달랐음) — 조건을 제거해서 고쳤습니다.

### 공통 에러 응답 포맷 통일

이전에는 API마다 FastAPI 기본 에러 형식(`{"detail": "..."}`)을 그대로 썼는데, `app/main.py`에
예외 핸들러를 추가해서 이제 **모든 API가 항상 같은 모양**으로 에러를 반환합니다:

```json
{"error": {"code": 404, "message": "유저 프로파일이 없습니다."}}
```

프론트(소현)는 이제 에러 처리 코드를 한 군데만 만들면 됩니다.

### Redis, 이제 진짜로 씁니다

`app/redis_client.py`에 `add_spending()` / `get_spending()` 두 함수를 만들었습니다. 거래
금액을 Redis의 `INCRBYFLOAT`(현재 값에 원자적으로 더하기)로 누적하고, 40일 뒤 자동 만료되게
TTL을 걸어뒀습니다. `GET /health`에서 Redis 연결 상태도 같이 확인할 수 있습니다.

## 6-2. 8/28 AI 절세장부 — 조소현님 분류 로직 실연동

조소현님이 `data_pipeline/categorizer.py`를 확장해서 실제 경비분류 프롬프트(Gemini,
few-shot 4개, 규칙 기반 폴백, 하이브리드 스킵 로직)를 완성해 전달해주셨습니다
(`expense_classifier.py` + `sample_expense_classify_response.json`). 이번에 은겸이 이걸
`GET /api/v1/expense/classify?user_id=...&limit=15`에 실제로 연결했습니다 —
DB에서 그 유저의 실제 거래를 읽어와 조소현님 로직(`classify_one()`)에 그대로 넘기고,
합의된 응답 모양으로 포장만 하는 얇은 라우터입니다.

**API 계약** (변경 금지 — 프론트 하은님과 이미 합의됨):
```json
{
  "transactions_queue": [
    {"id": 1, "merchant": "스타벅스", "amount": 15000, "ai_tag": "업무미팅", "prob": 92}
  ],
  "current_estimated_refund": 125000
}
```

**전달받은 파일에서 고친 것** (로직/프롬프트는 그대로, 실행 환경 버그만 수정):
- 🚨 `call_openai()` 안에 `os.environ.get(AQ.Ab8RN6...)`처럼 **따옴표 없이 API 키로 보이는
  문자열이 코드에 그대로 박혀 있었습니다.** 문법 오류라 실행은 안 됐겠지만, 실제 키를
  실수로 커밋한 것처럼 보입니다. **소현님 — 이 키가 진짜라면 지금 바로 재발급받아주세요**
  (파일이 팀 zip으로 여러 사람 거쳐 공유됐습니다). 이 버전은 `os.environ.get("GEMINI_API_KEY")`로
  정상화했습니다.
- `MOCK_MODE`가 파일에 두 번(7번째 줄 `False`, 46번째 줄 `True`) 정의되어 있어서 실제로는
  항상 Mock으로만 동작했습니다 → `GEMINI_API_KEY` 존재 여부로 자동 결정하도록 정리.
- `run_batch()`의 CSV 경로가 개인 컴퓨터 절대경로(`C:/Users/...`)로 하드코딩되어 있어서
  다른 환경에서 실행이 안 됐습니다 → `data/` 상대경로로 변경.

**검증**: 로컬 PostgreSQL의 실제 거래 데이터(4,978건)로 `GET /api/v1/expense/classify`를
호출해서 소현님이 보내주신 `sample_expense_classify_response.json`과 필드명·값 형태가
정확히 일치하는 것을 확인했습니다. 존재하지 않는 유저 조회 시 표준 에러 포맷(`404`)도
정상 동작합니다. `Mock_MODE`(=Gemini 키 없을 때)로 확인했고, 실제 Gemini 키를 넣고
호출하는 것까지는 이 환경에 키가 없어 확인하지 못했습니다 — 키가 준비되면 소현님/은겸님
중 아무나 `.env`에 `GEMINI_API_KEY`만 넣고 다시 호출해보면 됩니다(코드 변경 불필요).

**남은 일**: 지금은 "최근 N건"을 그때그때 다시 분류합니다. 나중에 결과를
`transactions` 테이블에 컬럼(`expense_prob`, `expense_tag`)으로 캐싱해서 스와이프로
승인/거절한 결과를 저장하는 기능을 붙이면 좋을 것 같습니다 (Tinder UI의 "넘기면 사라짐"
동작을 서버가 기억하게 하는 부분 — 시간 되면 8/30~31에).

## 6-3. 8/28 Isolation Forest 이상 탐지 모델 (은겸 담당, Day 4)

정답지(`data/mock_transactions_answer_key.csv`)를 까보면 이상 거래 263건 중 36건
(`R00x_위치급변` 21건 + `R00y_신규기기` 15건)은 애초에 룰 엔진으로 설계되지 않은
유형이라 R001~R007로는 절대 못 잡습니다. 이 두 유형을 잡는 게 목표였습니다.

**만든 것**: `app/anomaly_model.py` — scikit-learn `IsolationForest`를 학습해서
`models/anomaly_iforest.pkl`로 저장하고, `app/routers/risk.py`의 `/risk/assess`에서
룰 엔진과 함께 앙상블합니다. 모델 파일은 이미 학습해서 zip에 포함했으니 바로 씁니다
(데이터가 바뀌면 `python -m app.anomaly_model`로 재학습).

**앙상블 방식**: `combined_prob = 1 - (1-rule_prob) * (1-anomaly_prob)` (확률적 OR).
룰이 이미 CRITICAL이면 AI 결과와 무관하게 100점 그대로 — 기존 룰 기반 동작은 안 바뀝니다.
반대로 룰이 하나도 안 걸렸는데 AI가 확신하면(`anomaly_prob >= 0.6`), `rule_id="AI001"`로
`risk_events`에 남습니다. 실제 정답지 거래로 재현해보면:
- R00y_신규기기 샘플(새 기기로 결제) → 룰은 하나도 안 걸리지만 AI001이 MEDIUM/FLAG_FOR_REVIEW로 정확히 잡음 (`anomaly_prob=0.75`)
- 정상 거래 샘플 → LOW/ALLOW 그대로 유지 (오탐 없음)

**피처 튜닝 — 처음엔 8개였다가 4개로 줄였습니다.** 시간대(hour)/요일(dow) 순환 인코딩까지
넣었더니 오히려 신호가 희석돼서(IsolationForest가 분기마다 피처를 무작위로 골라 쓰다 보니
의미 없는 피처가 많을수록 진짜 신호가 있는 피처가 뽑힐 확률이 줄어듭니다), 타깃 유형 탐지가
8개 피처일 땐 6/36건이었는데 `amount_zscore`/`is_new_device`/`distance_from_prev_km`/
`merchant_rarity` 4개로 줄이니 20/36건으로 올랐습니다. 시간대 이상은 이미 R005(심야 대액)가
맡고 있으니 역할을 나눈 셈입니다.

**🐛 만들면서 발견해서 같이 고친 버그** (이상 탐지 피처 계산을 위해 히스토리를 제대로
불러오다가 발견함): `app/routers/risk.py`의 `_load_recent_history()`가
`datetime.utcnow() - timedelta(days=7)` 기준이었습니다. 즉 "지금 서버가 실행되는 시각"
기준이었는데, mock 데이터는 2026-05-25~08-22이고 이 서버가 실행되는 "지금"(8월 말)과
비교하면 7일 이내로 들어오는 데이터가 사실상 없어서 **R003(신규가맹점)/R004(불가능한
이동속도)/R006(단기반복)이 실제 DB 데이터로는 거의 항상 빈 이력을 받아 사실상 죽어있는
상태**였습니다. 평가 대상 거래 "자신의 시각" 기준으로 바꾸고 윈도우도 180일로 넓혔습니다.

**전체 재검증 (룰 엔진 + Isolation Forest, mock 데이터 4,978건 전체, 시간순 재현)**:

| | 이전 (룰 엔진만, 히스토리 버그 있는 채로 측정) | 지금 (버그 수정 + IF 앙상블) |
|---|---|---|
| Recall | 0.65 | **0.734** |
| Precision | 0.61 | 0.555 |

Recall은 올랐지만 Precision은 떨어졌습니다 — 이유를 추적해보니 **오탐 155건 중 109건이
R002(일일 누적 한도 초과)** 에서 나왔습니다. 히스토리 버그가 고쳐지면서 R002가 (전에는
거의 항상 비활성 상태였다가) 이제 실제로 하루 누적액을 제대로 계산하게 됐는데, Day
3에서 만든 `daily_limit` 산식(`평균거래액 × 일평균거래건수 × 3`)이 생각보다 타이트해서
정상적인 씀씀이도 자주 걸립니다. **이건 새 버그가 아니라 원래도 있었는데 버그 때문에
가려져 있던 문제**입니다. 지금 당장 고치진 않았고, `daily_limit` 배수를 완화하는 걸
다음 작업으로 남겨둡니다 (아래 7번 참고). AI 모델 자체의 오탐은 46건(정상 거래
4,715건 중 1.0%)으로 낮은 편입니다.

## 6-4. 8/30 정기결제 감지 + 예산 알림 임계값 (조소현님 로직 실연동)

소현님이 `data_pipeline/recurring_detector.py`를 새로 만들어서 전달해주셨습니다.
같은 유저+가맹점+비슷한 금액(±5%)이 대략 30일 간격으로 반복되면 "정기결제"로 판단하는
클러스터링 로직인데, 실제 mock 데이터로 돌려보니 11건(넷플릭스류 구독, 카카오택시 등)이
잡혔고 합성 테스트(넷플릭스 패턴은 잡고 불규칙한 스타벅스는 거름)도 통과했습니다.

**연동한 것**:
- `GET /api/v1/budgets/forecast` — 기존 "지금까지 지출 속도 × 남은 날"(`base_predicted_total`)에
  더해서, 이 카테고리에 속하는 가맹점의 정기결제 중 "이번 달 안에 아직 안 지나간 것"의
  예상 금액을 `recurring_payments` 필드로 추가하고 `predicted_total`에 합산했습니다.
  가맹점→카테고리 매칭은 `categorizer.py`의 `categorize_merchant()`를 그대로 재사용.
- `GET /api/v1/budgets/usage`, `POST /api/v1/budgets` — `crossed_thresholds` 필드 추가
  (예: `[50, 80]` = 50%/80%는 이미 넘었고 90% 이상은 아직). `budgets.alert_thresholds`는
  0.5/0.8 같은 "비율"로 저장돼 있어서 소현님 함수가 기대하는 %(50/80) 단위로 변환해서 넘겼습니다.

**설계 판단**: 소현님이 만든 `forecast_month_end()`는 "지금까지 쓴 돈"까지 자체적으로
다시 계산하는 독립 함수였는데, 이미 검증된 기존 Redis 기반 계산(`get_spending()`)이 있어서
그건 그대로 두고 "정기결제 예상액을 더하는" 부분만 가져와 얹었습니다. 두 군데서 "지금까지
쓴 돈"을 각각 다르게 계산하면 나중에 둘이 어긋날 수 있어서, 소스 오브 트루스를 하나로
유지하기 위한 선택입니다.

**실제로 검증한 것**: 실제 유저(노션 정기결제 보유)로 예산 생성 → 지출 기록 →
`crossed_thresholds`가 `[50]`으로 정확히 뜨는 것 확인. 정기결제 카테고리 필터링도
DB에서 직접 불러온 데이터로 검증(노션 → 업무용 카테고리로 정확히 매칭).

**⚠️ 데모 준비 시 알아둘 것**: `recurring_payments`는 "이번 달 안"인지를 서버가 실행되는
실제 오늘 날짜(`date.today()`) 기준으로 판단합니다. mock 데이터는 8/22까지라 감지된
정기결제 다음 예정일이 대부분 8월 말~9월 초예요 — 데모를 9월 초 이후에 하면 자연스럽게
채워지고, 그전에 미리 시연하려면 발표 리허설 날짜에 맞는 정기결제가 있는 유저를 골라서
보여주시면 됩니다 (이미 정기결제 실행 로그에 유저별 다음 예정일이 다 나와있어요).

**참고**: `expense_classifier.py`도 같이 재전달받았는데, 지난번 지적드린 API 키 노출
버그와 경로 문제를 소현님이 직접 고치신 버전이었습니다 — 저희가 이미 반영한 버전과
로직은 동일해서 기존 것을 그대로 유지했습니다. `.env`의 `GEMINI_API_KEY`는 아직 실제
키가 아니라 안내 문구만 있어서, 실제 키가 준비되면 그 줄만 교체하면 됩니다.

## 6-6. 8/30 프론트-백엔드 실연동 (데모 모드)

### 왜 "데모 모드"인가

없이, "미리 만들어둔 인물의 폰을 잠깐 구경하는" 방식으로 갑니다 — 화면 상단에 항상

### 검증

## 9. 9/2 두 번째 업데이트 — 배포 자동화(DB 자동 시딩) + 보안 점검

"배포만 하면 되게 완벽하게 만들어달라"는 요청을 받고, 위 "8. 9/2 업데이트"의 5번(DB가
빈 상태로 배포될 위험)을 실제로 고치고, API/보안도 한 번 더 점검했습니다.

**1) DB 자동 시딩 (신규) — `app/startup_seed.py`, `app/main.py`, `Dockerfile`**
앱이 시작할 때 스스로 (a) `sql/init.sql`을 실행해서 스키마를 만들고(이미 있어도 안전 —
전부 `IF NOT EXISTS`/`ON CONFLICT`라서 매번 실행해도 됩니다), (b) `transactions` 등
각 테이블이 비어있는지 확인해서 비어있는 단계만 `data_pipeline/ingestion.py` →
`scripts/build_user_profiles.py` → `scripts/seed_demo_personas.py` →
`scripts/seed_demo_income.py` 순서로 자동 실행하도록 만들었습니다. 이 스크립트들이
있는 `data/`·`scripts/`·`sql/` 폴더를 `Dockerfile`에 추가했습니다(전부 합쳐 1MB
미만이라 이미지 용량에 영향 거의 없음).

**실제로 완전히 빈 Postgres DB + 빈 Redis에 연결한 상태로 처음부터 서버를 띄워서
검증했습니다**: 스키마 생성 → 4,978건 거래 적재 → 35명 리스크 프로파일 계산 → 5명
페르소나 예산/리스크 이벤트 → 15개 수입 플랫폼까지 전부 자동으로 채워지고, 15초 안에
`/health`가 정상 응답하는 것까지 확인했습니다. 그 상태에서 서버를 재시작해도(=이미
데이터가 있는 상태) 다시 채우지 않고 즉시 뜨는 것, 데이터가 중복 생성되지 않는 것도
확인했습니다. 즉 **어떤 Postgres/Redis에 연결해주든(관리형 호스팅 포함) 이 이미지를
`docker build` + 실행만 하면 5개 페르소나 데모가 바로 동작합니다** — 배포 후 사람이
따로 스크립트를 돌릴 필요가 없습니다.

**2) 보안 점검**
- `docker-compose.yml`의 Postgres(5432)/Redis(6379) 포트가 모든 인터페이스에 열려
  있던 것을 `127.0.0.1`에만 묶도록 고쳤습니다. 이 파일 그대로 공인 IP가 있는 서버(VPS
  등)에 배포하면, 특히 Redis는 기본적으로 비밀번호 인증이 아예 없어서 인터넷 누구나
  접속할 수 있는 상태였습니다. api 컨테이너는 도커 내부망(`db:5432`, `redis:6379`)으로
  접속하므로 이 변경으로 앱 동작에는 영향이 없습니다 — 외부 접근만 막힙니다. (Railway·
  Render처럼 컨테이너 하나만 빌드해서 관리형 DB에 연결하는 방식으로 배포한다면 이
  `docker-compose.yml`은 애초에 안 쓰이니 해당 없음.)
- 하드코딩된 API 키/토큰/자격증명이 있는지 코드 전체를 검색했습니다 — `.env`/
  `.env.example`을 제외하면 없었고, 두 파일 다 실제 값이 아니라 빈 값/플레이스홀더만
  있습니다. `.env`는 `.gitignore`에 걸려 있어 깃에도, 이 zip에도 포함되지 않습니다.
- `app/security.py`의 `X-API-Key` 게이트(8/30 추가)는 그대로 뒀습니다 — `API_ACCESS_KEY`를
  비워두면 인증 없이 열려있는 상태인데, 일부러 키를 안 넣었습니다. 이 서비스는 로그인이
  아예 없는 공개 데모 모드(데이콘 운영진이 명시적으로 허용한 방식)라서 데이터 자체가
  전부 가짜이고, 프론트(`frontend/api.js`)에 넣는 키는 누구나 페이지 소스에서 볼 수
  있어 실질적인 보안 효과가 거의 없습니다. 오히려 배포 시 서버 쪽 `API_ACCESS_KEY`와
  프론트 쪽 `API_KEY`를 정확히 맞추지 않으면 전체 데모가 깨지는 위험이 더 커서, 이번
  배포에서는 끄는 쪽을 기본값으로 유지했습니다. 만약 이 API를 정말 잠그고 싶다면
  `.env`에 `API_ACCESS_KEY` 값을 넣고 `frontend/api.js`의 `API_KEY` 상수에 **정확히
  같은 값**을 넣어야 합니다(하나만 바꾸면 전체가 401로 막힙니다).
- SQL 인젝션: 모든 쿼리가 SQLAlchemy `text()` + 파라미터 바인딩(`:uid` 등)이라 문자열
  조합으로 값을 끼워넣는 곳이 없습니다(이번에 추가한 `income.py`도 동일한 패턴).
- 에러 응답이 스택 트레이스나 내부 경로를 노출하지 않는지도 다시 확인했습니다(8/30에
  이미 통일된 `{"error": {...}}` 포맷 그대로 유지).

## 10. 9/2 세 번째 업데이트 — 보안 강화 집중 점검 ("금융이라 보안이 제일 중요해" 요청)

gig-score/income(요약·목록·연결하기)/budgets/risk 등 전 API 엔드포인트를 curl로 직접
호출해서 응답 확인까지 전부 다시 통과시켰습니다.


**2) 보안 응답 헤더 미들웨어 (신규) — `app/security_headers.py`**

Content-Security-Policy, X-Content-Type-Options, X-Frame-Options, Referrer-Policy,
Permissions-Policy, (HTTPS일 때) Strict-Transport-Security를 모든 응답에 붙입니다.
CSP는 `frontend/*.html`이 페이지마다 인라인 `<script>` 블록을 쓰고 있어서
`script-src 'self' 'unsafe-inline'`로 뒀습니다 — 완벽하진 않지만(다음 단계로 인라인
스크립트를 전부 별도 .js로 옮기고 nonce 기반으로 강화할 수 있음), 외부 도메인에서
스크립트를 끌어오는 가장 흔한 XSS 공격 형태는 확실히 막습니다. Playwright로 6개 페이지를
전부 다시 열어서 CSP 때문에 깨지는 게 없는지(콘솔에 "Refused to..." 같은 CSP 위반 로그가
없는지, 인라인 스크립트·구글 폰트 스타일시트가 정상 동작하는지) 확인했습니다.

**3) Rate Limiting (신규) — `app/rate_limit.py`**

IP당 분당 120회로 `/api/v1/*` 요청을 제한합니다(정적 프론트 파일은 제외 — 페이지 하나
로드에도 여러 파일을 받아오니까요). 무차별 스크래이핑이나 `API_ACCESS_KEY` 무차별 대입
시도를 최소한이라도 막기 위함입니다. 지금은 단일 프로세스 배포(uvicorn 워커 1개)라
메모리 기반 카운터로 충분합니다 — 나중에 워커를 여러 개로 늘리면 Redis 기반 공유
카운터로 바꿔야 합니다(코드 주석에 남겨둠). 실제로 130회 연속 요청을 보내서 121번째부터
`429`가 나오는 것, 429 응답에도 보안 헤더가 정상적으로 붙는 것, `Retry-After` 헤더가
붙는 것까지 확인했습니다.

**4) Redis 비밀번호 인증 (신규) — `docker-compose.yml`, `.env`/`.env.example`**

포트를 `127.0.0.1`로 막아도(9번) "도커 내부망에 컨테이너 하나만 뚫리면 Redis는 완전
무방비"라는 문제가 남아있어서, `--requirepass`로 인증을 추가했습니다. `.env`의
`REDIS_PASSWORD`를 redis 서비스의 `command`와 헬스체크에 그대로 씁니다. `REDIS_URL`을
`redis://:<비밀번호>@redis:6379/0` 형식으로 바꾸면 `redis-py`(`app/redis_client.py`,
`app/database.py`)가 URL에서 비밀번호를 읽어 자동으로 인증하므로 **앱 코드는 수정하지
않았습니다** — 실제로 로컬에 `--requirepass`를 켠 별도 Redis 인스턴스를 띄우고 이
URL 형식으로 연결해서 `PING`부터 `budgets/usage` API 호출까지 정상 동작하는 것을
직접 확인했습니다.

**5) 컨테이너 비루트 실행 (신규) — `Dockerfile`**

지금까지 컨테이너 안에서 앱이 root로 돌고 있었습니다. 앱이 런타임에 `/app` 아래
아무 파일도 쓰지 않는 걸 확인했고(모델 학습 스크립트(`app/anomaly_model.py`의
`train()`)는 개발 중 수동으로만 돌리는 오프라인 스크립트라 컨테이너 안에서 실행되지
않음), 전용 비루트 유저(`appuser`)로 내려도 기능에 영향이 없어서 적용했습니다. 만에
하나 앱 코드에 원격 코드 실행으로 이어지는 취약점이 있어도, root 권한으로 컨테이너
전체를 장악하는 것보다는 피해 범위가 훨씬 줄어듭니다.

*(참고: 이 샌드박스 환경은 Docker 데몬이 실제로 뜨지 않아서 `docker build`/`docker run`
자체로 이 Dockerfile을 끝까지 실행해보진 못했습니다. 대신 실제 배포 이미지와 동일한
`requirements.txt`로 완전히 새 가상환경을 만들어 위 B-1의 전체 시나리오를 검증했고,
Dockerfile 변경 자체는 표준적인 `useradd` + `chown` + `USER` 패턴이라 위험도가 낮다고
판단했습니다. 배포 담당자가 `docker build`로 이미지를 만드는 시점에 한 번 더 정상
기동을 확인해주시면 가장 확실합니다.)*

### C. 의도적으로 남겨둔 한계 (강조해서 남겨둡니다)

- **IDOR(다른 사람 데이터 조회) 미차단**: `user_id`를 쿼리 파라미터로 그대로 받기 때문에,
  API를 호출할 수 있는 사람은(=`API_ACCESS_KEY`를 알거나, 지금처럼 꺼둔 상태라면 누구나)
  `user_id`만 바꿔서 다른 사람의 예산/리스크/절세장부/수입 데이터를 조회할 수 있습니다.
  이건 진짜 로그인·세션 기반 인가(authorization)가 있어야 막을 수 있는데, 이번 데모는
  **로그인이 아예 없는 공개 데모 모드**(데이콘 운영진이 명시적으로 허용한 방식)이고
  데이터 자체가 5개 페르소나 + 일반유저 모두 처음부터 끝까지 가짜(mock)라서, 실제
  피해로 이어지는 개인정보 유출이 아닙니다. **다만 이 구조를 실제 서비스(진짜 계좌·진짜
  사용자)로 그대로 확장한다면 가장 먼저 넣어야 하는 게 바로 이 부분입니다** — 세션
  기반 로그인을 붙이고, 모든 API가 "요청자 본인의 user_id"만 조회하도록 서버에서
  강제해야 합니다.
- API_ACCESS_KEY는 여전히 기본값이 꺼진 상태입니다(9번에서 설명한 이유 그대로 — 프론트
  JS에 키가 그대로 노출되는 구조라 실질적 방어 효과가 적고, 서버/프론트 키 불일치로
  데모 전체가 깨질 위험이 더 큼). 켜고 싶다면 `.env`의 `API_ACCESS_KEY`와
  `frontend/index.html` 상단의 `API_KEY` 상수(11번 참고, 9/5부터 `frontend/api.js`가
  아니라 이 파일로 옮겨졌습니다)를 정확히 같은 값으로 맞추면 됩니다.
- Rate limiting은 단일 프로세스 전제입니다(위 B-3 참고) — 멀티 워커로 배포를 바꾸면
  Redis 기반으로 교체해야 합니다.
- CSP의 `script-src`에 `'unsafe-inline'`이 남아있습니다(위 B-2 참고) — 완전히 없애려면
  프론트 인라인 스크립트를 전부 별도 `.js` 파일로 분리하는 리팩터링이 필요합니다.

### 12-2. 세금·건강보험료를 실제 산식으로 (`app/tax.py`, `GET /api/v1/tax/estimate/{user_id}`)

기존에는 "월평균 수입 × 8%(세금), × 7%(건보료)"였고, 코드 주석에도 근거가 "프리랜서에게
흔히 권장되는 관행"이라고만 적혀 있었습니다. 이 서비스의 핵심 주장이 "1~2년 뒤 맞을
세금·건보료를 지금 알려준다"인 이상 그 숫자에 근거가 있어야 해서 실제 제도로 교체했습니다.

- **종합소득세**: 단순경비율(업종별) → 기본공제 150만원 → 과세표준 → **8단계 누진세율표**
  → 지방소득세 10% → **기납부 원천징수 3.3% 차감**. 결과가 음수면 환급액입니다.
- **건강보험료**: 2026년 요율 **7.19%** + 장기요양보험료(건보료의 12.95%). 직장가입자는
  급여 외 소득 **2,000만원 초과분**에만 소득월액보험료(전액 본인 부담), 지역가입자는 소득 전체.

실제 출력 (배포 서버 기준):

| 페르소나 | 5월 종합소득세 | 건강보험료 | 경고 |
|---|---|---|---|
| 김민철(배달 투잡) | 36.8만원 **환급** | 월 0원 | "앞으로 612만원 더 벌면 2,000만원 기준을 넘습니다" |
| 박지수(프리랜서) | 18.1만원 **환급** | 월 37.7만원(지역) | "피부양자 자격 기준 초과" |
| 이하늘(개발자+외주) | 42.7만원 **환급** | 월 17.8만원(직장) | "초과분 2,629만원은 회사 지원 없이 전액 본인 부담" |

> 발견: 3.3% 원천징수는 단순경비율을 적용하면 대부분 **과납**이라 오히려 환급이 나옵니다.
> 그래서 화면 문구도 "세금 떼어두세요"가 아니라 "5월에 돌려받아요 / 건보료는 이만큼 나갑니다"로
> 바꿨습니다. **2,000만원 경계를 넘기 전에 미리 알려주는 것**이 이 기능의 핵심입니다.

한계는 `app/tax.py` 상단 docstring에 명시했습니다(인적공제·세액공제·다른 소득·재산 점수 미반영).

### 12-3. 프론트엔드 전면 재작성 (`frontend/index.html`)

기존 화면은 폰 목업 형태라 데스크톱으로 심사할 때 제품이 아니라 목업처럼 보였습니다.
토스 디자인 언어(Pretendard, 토스 블루, 18~20px 라운드, 테두리 대신 여백/그림자) 기준으로
다시 만들었고, 구조를 두 화면 + 3단으로 나눴습니다.

1. **사례 선택 화면** — 3명 카드에 각자의 현재 현금흐름 상태(안전/주의/위험)와 부족 예상일을
   미리 띄워서, 고르기 전에 무엇을 보게 될지 알 수 있게 했습니다.
2. **대시보드**
   - 1단 요약: "9월 26일, 35일 뒤에 잔고가 30만원 아래로 떨어질 것 같아요" + 현재 잔액 /
     쓸 수 있는 돈 / 다음 입금
   - 2단 할 일: 실제 데이터로 계산한 행동 3개 (플랫폼 연결 버튼, 건보료 경고, 예산 초과 등)
   - 3단 탭: 현금흐름 / 수입 / 지출 / 거래 보안

**읽기 전용이 아니라 실제로 조작됩니다** — 아래 셋은 전부 서버 상태를 바꾸고 결과를 다시 불러옵니다.

| 기능 | 엔드포인트 | 눌렀을 때 실제로 일어나는 일 |
|---|---|---|
| 거래 위험도 즉시 검사 | `POST /api/v1/risk/assess` | 룰 엔진 7종 + Isolation Forest 앙상블이 판정하고 `risk_events`에 기록 → 옆 탐지 이력이 갱신 |
| 수입 플랫폼 연결 | `POST /api/v1/income/sources/{id}/connect` | 연결된 플랫폼만 예측에 반영되므로 **45일 곡선과 세금 추정이 실제로 바뀜** |
| 최소 안전잔액 변경 | `PUT /api/v1/shield/{id}/settings` | 저장 후 시뮬레이션 재계산 → 부족 예상일이 바뀜 |
