1. 서비스 명칭

SideGig — N잡러의 현금흐름·세금 예측 금융 비서

여러 플랫폼에서 불규칙하게 들어오는 수입을 한곳에 모아, 다음 정산까지 잔고가 버티는지를 하루 단위로 예측하고 세금·건강보험료를 미리 알려주는 웹 서비스입니다.

2. 아이디어 기획 핵심내용(요약)

  • 대상: 배달·프리랜서·콘텐츠 등 둘 이상의 플랫폼에서 소득을 얻는 N잡러(플랫폼 노동자·프리랜서).
  • 문제: 수입은 플랫폼마다 정산 주기가 달라 들쭉날쭉한데, 고정비는 매달 같은 날 빠져나간다. 세금·건강보험료는 1~2년 뒤에 고지서로 뒤늦게 도착한다.
  • 해결: ① 플랫폼별 정산 주기를 학습해 45일 현금흐름을 일 단위로 예측하고 잔고 부족 시점을 알림 ② 실제 세법·건보료 산식으로 내년 5월 종합소득세와 월 건강보험료를 추정하고 2,000만원 경계를 넘기 전에 경고 ③ 규칙 엔진과 이상탐지 모델로 본인이 하지 않은 결제를 차단 ④ 생성형 AI가 위 계산 결과를 문장으로 설명하고 업무경비를 분류 ⑤ 상황별로 고려할 수 있는 선택지를 근거와 함께 안내(특정 상품 권유 아님) ⑥ 보는 사람이 자기 수입 조건을 직접 넣어 같은 예측을 받아볼 수 있음.
  • 차별점: 은행 앱은 "이미 쓴 돈"을 보여주지만, SideGig는 은행이 볼 수 없는 플랫폼 정산 데이터로 "앞으로 벌어질 일"을 계산한다.
  • 구현 수준: 아이디어가 아니라 실제 동작하는 웹 서비스로 구현·배포 완료(위 URL). 화면에서 누르는 동작이 실제 서버 상태를 바꾸고 예측이 재계산된다.

3. 문제 정의 및 제안 배경

3-1. 대상 고객과 채널을 이렇게 정한 이유

고객: N잡러(플랫폼 노동자·프리랜서). 이들은 소득이 없어서가 아니라 소득의 모양이 불규칙해서 금융에서 불리해지는 집단입니다. 기존 금융 서비스는 "매달 같은 날 같은 금액이 들어오는 사람"을 전제로 설계돼 있어, 정산 주기가 제각각인 이들에게는 예산·신용·세금 어느 쪽도 맞지 않습니다.

채널: 데스크톱 웹. 세금·건보료·현금흐름은 표와 그래프를 동시에 놓고 봐야 이해되는 정보량입니다. 모바일 단독 화면에서는 "며칠 뒤 얼마가 부족한지"를 한눈에 비교하기 어렵다고 판단해 웹을 1차 채널로 하고, 좁은 화면에서도 무너지지 않도록 반응형으로 구현했습니다.

3-2. 구체적인 문제점

문제지금 무슨 일이 일어나는가기존 금융 서비스가 못 하는 이유
정산 주기 불일치 배달은 주 단위, 프리랜서 용역은 2주~월 단위, 콘텐츠 수익은 월 단위로 들어온다. 고정비는 날짜가 고정돼 있어 "수입이 오기 전에 돈이 먼저 나가는" 구간이 주기적으로 생긴다. 은행은 자행 계좌의 입출금만 본다. 어느 플랫폼에서 며칠 주기로 정산되는지는 알 수 없다.
세금·건보료의 시차 3.3% 원천징수는 실제 세액과 다르고, 건강보험료는 소득이 잡힌 뒤 시차를 두고 부과된다. 특히 연 2,000만원을 넘는 순간 피부양자 자격 상실 또는 소득월액보험료가 새로 발생하는데, 대부분 넘고 나서 고지서로 안다. 은행 앱에 세법·건보료 계산 기능이 없고, 흩어진 소득을 합산할 방법도 없다.
소득 증빙의 공백 여러 플랫폼 정산 이력이 하나의 소득으로 인정되지 않아, 실제로 버는 만큼의 신용을 인정받지 못한다. 금융기관이 참조할 표준화된 플랫폼 소득 데이터가 없다.

3-3. 사용자 인터뷰

배달·프리랜서·부업형 N잡러 [N]명을 대상으로 각 20~30분 인터뷰를 진행했습니다(2026년 9월).

  • [N]명 중 [M]명이 최근 6개월 내 "수입이 들어오기 전에 고정비가 먼저 빠져나가" 곤란했던 경험이 있었습니다.
  • 다음 달 예상 수입을 파악하는 방법으로 [M]명이 "머릿속으로 대충"이라고 답했습니다.
  • 부업 소득이 연 2,000만원을 넘으면 건강보험료가 별도 부과된다는 사실을 [M]명이 모르고 있었습니다.
  • 인용: "[실제 발언]" ([직업], 경력 [N]년)
왜 지금인가 — 플랫폼 노동은 이미 소수의 예외가 아니라 하나의 고용 형태로 자리 잡았지만, 금융 서비스의 기본 전제(정기적 급여)는 그대로입니다. 이 간극이 이 서비스의 출발점입니다.

  • 거래 내역에서 규칙적으로 반복되는 결제를 찾아(간격 중앙값의 ±25% 이내) 미래 지출로 투사한다.

  • 수입 변동계수가 클수록 세금·건보료 준비금을 더 보수적으로 잡는다.

5-2. 생성형 AI(Gemini)의 역할 — 두 곳에 실제 적용

적용 지점하는 일왜 생성형 AI여야 하는가
AI 브리핑
(첫 화면 상단)		 계산이 끝난 수치(잔액·가용액·부족 예상일·세금 정산액·건보료·위험 사유)를 입력받아 2~3문장의 상황 설명과 권고 한 줄을 생성.
예: "현재 잔액은 145만원으로, 35일 뒤 최소 안전잔액인 30만원 이하로 떨어질 것으로 예상됩니다. 월 추정 건강보험료 38만원 등을 제외한 가용액은 107만원입니다. → 잔고 부족에 대비해 단기 지출을 줄이세요."		 숫자는 규칙으로 정확히 계산되지만, 여러 지표에 걸친 인과를 이어 붙여 설명하는 일은 규칙으로 쓰기 어렵고 사람마다 상황이 달라 템플릿으로는 어색해진다.
업무경비 자동 분류
(지출 탭)		 직업·가맹점·시간대·금액을 받아 업무 경비 인정 가능성(%)과 태그를 생성. 예: 어도비 29.9만원 → "업무용구독/툴" 98%, 무신사 8.97만원 → "개인지출" 12%. 가맹점명은 종류가 무한하고 같은 가맹점도 직업에 따라 판단이 달라진다. 규칙 목록으로는 새로운 가맹점을 영원히 따라잡을 수 없다.

5-3. 신뢰성 설계 — 환각·장애를 어떻게 막았는가

  • 숫자를 생성시키지 않는다: 모델에는 이미 계산이 끝난 값만 전달하고, 새로운 수치·사실을 만들어내지 말라고 지시한다. 금액 계산은 전부 결정론적 코드가 담당한다.
  • 실패해도 화면이 비지 않는다: 모델 호출이 실패하면 동일한 수치로 만든 문장(브리핑) 또는 규칙 기반 분류(경비)로 자동 강등된다. 실제로 개발 중 모델 서비스 종료(404)와 과부하(503)를 모두 겪었고, 두 경우 모두 서비스는 정상 동작했다.
  • 모델 이중화: 여러 모델을 순서대로 시도하고, 마지막 호출의 성공 여부를 /health에 그대로 노출해 "키는 있는데 호출은 실패 중"인 상태를 숨기지 않는다.
  • 비용·지연 관리: 동일 입력의 결과를 캐싱해 화면 재방문 시 재호출하지 않는다(측정: 첫 호출 3.6초 → 이후 0.2초).

5-4. 생성형 AI 외 분석 모델

  • 규칙 엔진 7종(R001~R007): 단건 한도, 일일 누적 한도, 신규 가맹점, 이동 속도, 심야 고액, 단기 반복, 해외 결제.
  • Isolation Forest: 금액 z-score·신규 기기 여부·직전 거래와의 거리·가맹점 희소성 4개 피처로 학습. 규칙이 설계상 잡지 못하는 유형(위치 급변·신규 기기)을 담당.
  • 앙상블: 확률적 OR — 1 − (1−규칙확률)×(1−이상확률). 규칙이 이미 위험이면 결과는 그대로 유지된다.

6-1-1. 금융소비자 보호를 고려한 설계

상황에 맞는 안내를 제공하되, 특정 금융상품·금융회사를 권유하지 않습니다. 자본시장법상 투자권유와 대출모집은 등록된 사업자만 수행할 수 있고, 무엇보다 잔고 부족이 예측된 이용자에게 고금리 신용대출을 먼저 제시하는 것은 이용자에게 해가 될 수 있다고 판단했습니다. 대응 가이드는 비용이 낮은 선택지부터 배치합니다 — 정산일 확인 → 고정비 이체일 조정 → 보유 한도·정책 지원 제도 확인 → (마지막) 대출은 총 상환액을 계산한 뒤 결정. 각 항목에는 왜 지금 그 상황인지 계산 근거와 주의점을 함께 붙입니다.

6-2. 금융 서비스 제공자가 얻는 것

  • 보이지 않던 소득의 가시화: 플랫폼 정산 이력은 은행이 확보하기 어려운 데이터다. 이를 표준화해 제공하면 N잡러 여신 심사의 공백을 메울 수 있다.
  • 소득 안정성 지표(Gig Score): 플랫폼 연결 성실도·지출 안정성·업무경비 인정률을 1000점 척도로 산출. 씬파일러(금융 이력 부족 고객) 심사의 보조 참고 지표로 활용 가능합니다. 현 단계에서는 연체·부도 등 실제 신용사건과의 상관을 검증한 바 없으므로 신용평가 모형이 아니라 관리 성실도를 수치화한 자체 지표로 규정합니다.
  • 이상거래 대응 비용 절감: 규칙과 모델의 앙상블 판정을 근거와 함께 제공해 확인 요청·차단의 설명 가능성을 높인다.

6-3. 수익 모델

단계내용
1단계
B2C		 기본 기능(현금흐름 예측·세금 추정)은 무료로 제공해 사용자를 모읍니다. 세금 신고 시즌의 상세 리포트, 다년치 이력 보관, 알림 고도화 등을 유료 구독으로 둡니다. 다만 이 시장은 이미 경쟁이 있어 단독 수익원으로 보지 않습니다.
2단계
B2B (본류)		 플랫폼 정산 이력을 표준화한 소득 안정성 지표를 금융기관에 제공합니다. 은행·카드사 입장에서 N잡러는 소득이 있어도 증빙이 어려워 심사가 막히는 고객군인데, 이 지표는 그 공백을 메웁니다. 사용자가 명시적으로 동의한 경우에만 전달하며, 데이터 제공 건당 또는 구독 형태로 과금합니다.
3단계
제휴		 사용자 동의를 전제로, 상황에 맞는 금융 서비스로 연결하는 제휴 모델. 단 이 단계는 투자권유·대출모집에 필요한 인허가를 갖춘 뒤에만 진행합니다(현재 MVP는 특정 상품을 권유하지 않습니다).

6-4. 확장 방안

단계내용
단기오픈뱅킹·마이데이터 연동으로 잔액·정산 데이터를 실제로 수집(현재는 사용자 입력·시연 데이터). 세액공제·인적공제 반영으로 세금 추정 정밀화.
중기세션 로그인 기반 인가 도입, 알림(정산 지연 감지·기준 초과 임박) 푸시, 플랫폼별 공식 API 연동 확대.
장기Gig Score를 금융기관에 제공하는 대안신용평가 데이터 서비스로 확장. 소상공인·1인 사업자로 대상 확대(동일 문제 구조: 불규칙 매출 + 뒤늦은 세금).
타 영역"불규칙한 수입 + 고정 지출 + 뒤늦은 정산" 구조는 프리랜서 계약, 농수산물 판매, 공연·예술 분야 등에도 동일하게 존재한다. 현금흐름 예측 엔진은 그대로 이식 가능하다.

MVP의 한계를 분명히 밝힙니다 — 표시되는 인물·거래·정산 내역은 모두 시연을 위해 생성한 가상 데이터입니다. 세금·보험료는 확정 금액이 아닌 추정치이며(인적·세액공제, 재산 점수 미반영), Gig Score는 금융기관의 신용점수가 아닙니다. 현재는 로그인이 없는 공개 시연 구조라, 실서비스 전환 시 세션 기반 인가가 선행되어야 합니다.
